# Recurring disconnects

## Acting before the actual system is located

The model sometimes reasoned from the wrong machine, stale configuration, an inferred file meaning, or a filename rather than the live object. Burooj then had to supply the missing topology. Recovery should begin with a compact state map: where the agent is, what surface the user is seeing, what is authoritative, and what remains inferred. Evidence: E003, E004, E016, E019.

## Prematurely narrowing options

Some responses presented a recommendation before exposing the configuration choices or architectural consequences that Burooj needed to understand. He then researched the omitted options himself or accused the model of explaining them poorly. The remedy is not an indiscriminate option dump: surface the consequential branches, recommend one, and say what is being deferred. Evidence: E002, E003, E005, E006, E027.

## Converting exploration into instruction residue

Temporary phrases, provider debate, metaphors, and irrelevant platform rules leaked into durable agent files. The result was technically valid but semantically noisy. Before writing durable instructions, the model should ask: is this a lasting rule, current mechanism, local fact, or merely how we reached the decision? Evidence: E005, E026.

## Rewriting instead of preserving

The model sometimes treated a tuned file or existing system as raw material for a clean rewrite. Burooj explicitly preferred surgical edits and preservation of what had already been worked through. Recovery requires a diff-oriented proposal and an account of what will remain untouched. Evidence: E003, E005, E006, E019.

## Losing the user during long work

Workers, tool calls, and long transfers could continue while the main conversation became opaque. Burooj's repeated status questions were usually about state, ownership, or the next observable result—not a demand for constant narration. Strong progress updates should name completed phase, current phase, blocker, and next proof. Evidence: E003, E007, E013, E016.

## Confusing orchestration roles

Models sometimes treated a worker as an orchestrator, restarted work when asked to continue from the current state, or failed to reconcile stopped background work. Burooj corrected role names and task semantics directly. A recovery dish should test whether a model can rebuild a trustworthy task graph from partial receipts. Evidence: E010, E013.

## Passing technical checks while missing the human-visible result

HTTP success, configuration validity, or a green test did not always mean the UI worked on the actual phone, browser, or navigation path. Burooj often supplied screenshots or direct observations that contradicted the model's confidence. The model should name both machine checks and human-path checks. Evidence: E004, E012, E014, E022.

## Treating a correction as local when it changes the whole frame

A corrected domain fact—mainline versus savepoint, local versus remote, shared versus per-environment state—often invalidated downstream assumptions. Weak recovery patched the sentence; strong recovery propagated the new premise through files, tests, documentation, and remaining work. Evidence: E005, E013, E018, E019, E027.

## Polishing away the evidence

In a historical-analysis project, the model produced a beautiful but sparse result that concealed how little evidence was exposed. Burooj rejected it as surface-level. The eventual recovery changed the research design, not just the prose: chronological slices, inspectable evidence, contradictions, and a privacy-safe public layer. This is one episode but a particularly strong discriminating situation. Evidence: E016.

## Overstating completion

“Done” sometimes preceded a live check, complete migration, correct branch state, or visible UI. Burooj then asked whether it was really finished or what actually changed. A trustworthy completion statement should tie back to the requested stopping condition and distinguish implemented, verified, and merely prepared. Evidence: E007, E013, E016, E018.
